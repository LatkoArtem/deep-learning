# Лабораторна робота 4. FP32 проти INT8

## Мета

Експортувати модель ResNet-18 з ЛР3 у ONNX, виконати статичну INT8-квантизацію після навчання та порівняти точність, розмір файлів і затримку на CPU.

## Підготовка після клонування

Для роботи потрібні Python 3.12, [`uv`](https://docs.astral.sh/uv/getting-started/installation/) і датасет Intel Image Classification. Сам датасет не зберігається в GitHub. Завантаж його з [Kaggle](https://www.kaggle.com/datasets/puneet6060/intel-image-classification) і розпакуй так, щоб від кореня репозиторію були шляхи:


Можна використати інше розташування; тоді передай його у `--data`. Checkpoint `lab3/lab3_model.pt` і поділ `lab3/split.csv` уже входять до клонованого репозиторію.

## Запуск

Команди нижче починаються з кореня клонованого репозиторію. Спершу створи середовище ЛР4:


```powershell

```

Скрипт перевіряє дані, експортує моделі та записує повний звіт у `lab4_results.json`. Він також створює `.onnx` файли, які ігноруються Git. JSON вже збережений у репозиторії; повторний запуск оновить його у твоїй робочій копії.

Notebook `lab4.ipynb` показує протокол і читає JSON. Після створення JSON, залишаючись у теці `lab4`, відкрий його так:

```powershell
uv run --locked --with jupyter --with ipykernel jupyter notebook lab4.ipynb
```

За штатного запуску скрипт перевіряє, що ноутбук підключений до живлення. Параметр `--allow-battery` потрібен лише для заміру під час відключення електрики; такий запуск буде позначений як відхилення, і таблиці README потрібно буде оновити за JSON після повторного запуску від мережі.

## Дані та модель

Використано checkpoint `lab3/lab3_model.pt`: ResNet-18 з головою на шість класів. Порядок класів: `buildings`, `forest`, `glacier`, `mountain`, `sea`, `street`. Розмір береться з checkpoint (`160`). Кожне зображення відкривається через Pillow у RGB і проходить `Resize((160,160))`, `ToTensor()` та нормування ImageNet:

$$
\widetilde{x}_c=\frac{x_c-\mu_c}{\sigma_c},\qquad
\mu=(0.485,0.456,0.406),\quad
\sigma=(0.229,0.224,0.225).
$$

Тестові зображення обробляються в порядку рядків `lab3/split.csv`. Перевірки: train — 1200 зображень, сума числових імен 11 993 084; test — 1502, сума 33 351 444. Калібрування використовує тільки train: 1200 рядків сортуються за іменем, потім беруться індекси `default_rng(0).permutation(1200)[:200]`. Контрольна вибірка: 200 зображень, сума імен 1 921 470; `buildings` 40, `forest` 35, `glacier` 36, `mountain` 33, `sea` 29, `street` 27. Test у калібруванні не використовується.

## Експорт і квантизація

Експорт: `torch.onnx.export`, `dynamo=False`, opset 17, назви тензорів `input` і `logits`, динамічна вісь batch; модель у `eval()`. Експорт перевіряється на всіх 1502 тестових зображеннях за максимальною абсолютною різницею логітів і збігом класів PyTorch/ONNX.

Перед статичною квантизацією виконується `quant_pre_process(..., skip_symbolic_shape=True)`. Основний варіант використовує QDQ, активації QUInt8, ваги QInt8, `per_channel=True`, MinMax; решта параметрів лишається типовою. Усі 200 калібрувальних зображень подаються окремо, розміром `1 × 3 × 160 × 160`.

| Перевірка експорту | Результат |
|---|---:|
| Максимальна абсолютна різниця логітів PyTorch / ONNX | 1.1444 × 10⁻⁵ |
| Збіг класів PyTorch / ONNX | 1.0000 |
| Macro-F1 PyTorch / ONNX | 0.89121055 / 0.89121055 |
| Conv-вузлів / BatchNormalization-вузлів | 20 / 0 |

Похибка логітів менша за контрольну межу `10⁻³`; контроль експорту пройдено.

### Прогноз досліду per-tensor — записано до запуску

Коли кожен вихідний канал згортки має власний діапазон ваг, канали з малими вагами не втрачають точність через масштаб великого каналу. Тому прогнозую, що `per_channel=False` знизить згоду прогнозів із FP32. Водночас очікую, що парна зміна accuracy залишиться в межах шуму за правилом `|b-c| ≤ 2√(b+c)`; macro-F1 може трохи змінитися, але перевірю його окремо за фактичними значеннями.

Для згортки з вагами `W ∈ ℝ^(C_out×C_in×k_H×k_W)` діапазон каналу та відношення обчислюються так:

$$
\alpha_c=\max |W_c|,\qquad
r=\frac{\max_c\alpha_c}{\mathrm{median}_c\alpha_c},\qquad
\Delta b\approx\log_2(r).
$$

За одним масштабом на весь тензор канали з типовим максимальним значенням витрачають приблизно `log₂(r)` бітів діапазону на користь найбільшого каналу. Для всіх Conv-вузлів FP32-графа вказані три найбільші `r` та медіана `r`.

## Якість і парне порівняння

Macro-F1, accuracy і згода класів рахуються на тих самих 1502 test-зображеннях. `b` — INT8 правильний, FP32 помилився; `c` — INT8 помилився, FP32 правильний:

$$
\Delta_{acc}=acc_{INT8}-acc_{FP32}=\frac{b-c}{n},\qquad
SE(\Delta_{acc})\approx\frac{\sqrt{b+c}}{n},\qquad n=1502.
$$

Якщо `|b-c| ≤ 2√(b+c)`, різниця accuracy не відрізняється від шуму. Для порівняння наводиться також стандартна похибка однієї моделі `√(p(1-p)/n)`. Парна похибка менша, коли FP32 та INT8 здебільшого дають ті самі прогнози.

| Варіант | Macro-F1 | Accuracy | Згода класів з FP32 | b | c | Δaccuracy ± SE |
|---|---:|---:|---:|---:|---:|---:|
| PyTorch FP32 | 0.8912 | 0.8895 | — | — | — | — |
| ONNX FP32 | 0.8912 | 0.8895 | 1.0000 | — | — | — |
| ONNX INT8, per-channel | 0.8797 | 0.8768 | 0.9387 | 35 | 54 | −0.01265 ± 0.00628 |
| ONNX INT8, per-tensor | 0.8931 | 0.8915 | 0.9794 | 16 | 13 | +0.00200 ± 0.00359 |

Для per-channel `|b-c| = 19`, а `2√(b+c) = 18.87`, отже зміна accuracy трохи перевищила шумовий поріг і її напрям — вниз. Для per-tensor `|b-c| = 3 ≤ 10.77`, тому зміна accuracy від шуму не відрізняється. Згода прогнозів per-tensor 97.94%, вища за 93.87% у per-channel; прогноз, що згода знизиться, не справдився. Per-channel дав гірші макро-F1 та accuracy в цьому запуску. Це результат конкретної моделі й ONNX Runtime.

Стандартна похибка однієї FP32-моделі дорівнює 0.00809. Парна похибка для per-channel — 0.00628 (у 1.29 раза менша), а для per-tensor — 0.00359 (у 2.26 раза менша). Парна оцінка враховує лише зображення, на яких правильність двох варіантів різниться. Для per-channel таких змін більше, тому виграш від парного порівняння скромніший.

## Затримка на CPU

Сесії створюються до вимірювання; використовується `CPUExecutionProvider`, один внутрішній та один міжопераційний потік, batch 1. На першому тестовому зображенні робляться 20 прогрівальних викликів, а потім 100 замірів у кожному з трьох раундів. У виміряний інтервал входить лише один `session.run`. Для кожного варіанта p50 і p95 рахуються за всіма 300 вимірами. p50 раундів потрібні для правила перекриття діапазонів.

| Варіант | Файл, MB | p50, ms | p95, ms | p50 за раундами, ms |
|---|---:|---:|---:|---|
| FP32 | 44.7089 | 38.2729 | 43.0878 | 38.9822; 38.0415; 37.9192 |
| INT8 | 11.2969 | 21.5592 | 24.3073 | 21.7353; 21.7711; 21.1861 |

Прискорення `p50_FP32 / p50_INT8 = 1.7752`. Діапазони p50 `[37.9192, 38.9822]` та `[21.1861, 21.7711]` мс не перетинаються, отже за правилом роботи зниження затримки виміряне. У кожному раунді спершу замірювався FP32, потім INT8; для кожної сесії виконувалися 20 прогрівів.

### Висновок

FP32-модель займає 44.7089 MB, INT8 — 11.2969 MB, тобто файл став у 3.96 раза меншим. p50 скоротився з 38.2729 до 21.5592 ms, p95 — з 43.0878 до 24.3073 ms; діапазони раундових p50 не перетинаються, тому зміна виміряна за критерієм роботи. Ці заміри виконані при мережевому живленні.

Для per-channel accuracy знизився на 1.265 відсоткового пункту й трохи перевищив шумовий поріг; macro-F1 знизився з 0.8912 до 0.8797. Для per-tensor accuracy зріс на 0.200 пункту, але різниця в межах парного шуму; macro-F1 становив 0.8931. Перед запуском прогнозувався нижчий збіг прогнозів per-tensor, але фактично він виявився вищим: 0.9794 проти 0.9387 для per-channel.

CPU runtime визначив AVX2. AMD перелічує AVX2 для Ryzen 5 6600H, але не VNNI; це узгоджується з поясненням ONNX Runtime, що на x86 швидкість INT8 залежить від цілочисельних інструкцій і VNNI може дати додаткове прискорення. Отже відсутність VNNI тут є висновком із переліку інструкцій процесора. Скорочення файлу майже вчетверо дало прискорення p50 у 1.78 раза; час не скоротився вчетверо, бо на нього впливають підтримка цілочисельних інструкцій та накладні витрати квантизації. Для цього CPU INT8 зменшила файл і затримку, але per-channel помітно погіршив якість; per-tensor зберіг якість у межах парного шумового критерію.
